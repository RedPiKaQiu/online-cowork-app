## Context

现有阶段 1 的 Drizzle 模型已存储项目、成员和任务，阶段 2 已为项目链接生成原始令牌并保存带 pepper 的哈希。当前首页仍加载演示数据，尚没有按链接读取持久化看板的路径。

## Goals / Non-Goals

**Goals:**

- 在一个服务端读取边界验证令牌、过滤软删除项目并构造最小 DTO。
- 同时支持服务端页面初始渲染和供后续客户端刷新使用的 JSON 快照接口。
- 复用既有看板展示组件，同时禁止其在阶段 3 发起持久化写入。

**Non-Goals:**

- 不实现任务、成员或项目元数据的写接口、乐观更新或实时同步。
- 不改变管理员项目管理流程、令牌生成策略或数据库表结构。

## Decisions

### 在服务层按令牌哈希解析项目

读取服务将使用既有的 SHA-256 与 `PROJECT_TOKEN_PEPPER` 计算请求令牌哈希，并在查询中同时限定哈希和 `deleted_at IS NULL`。这样页面和 API 共享同一权限与 DTO 边界；相比在路由中直接查询，可避免两个入口的过滤条件漂移。

### 使用显式 DTO 和状态分组

服务层只选择浏览器所需字段，并将平铺任务按 `box`、`todo`、`done` 分组。数据库查询按状态和 position 排序，以便 DTO 稳定且客户端不需要了解数据库字段名或重新排序。直接返回 ORM 实体被排除，因为它可能意外暴露令牌哈希或未来内部字段。

### 页面优先服务端加载，客户端仅负责展示

`/p/[token]` 将在服务端加载快照后把它传给专用只读 `BoardClient`。不存在时由同一页面渲染统一不可用视图。JSON API 复用服务层，供后续阶段的客户端缓存和实时恢复使用；不在本阶段引入前端数据请求库。

## Risks / Trade-offs

- [令牌被复制后任何持有者均可读取项目] → 这符合匿名链接访问模型；管理员重置链接会立即使旧令牌失效。
- [每次页面加载查询三个数据集] → 项目规模小且查询均以 project ID 和任务排序索引限定；后续可在测量后合并或缓存。
- [原 Demo 的编辑控件会暗示写入可用] → 阶段 3 的客户端只渲染只读看板，阶段 4/5 再接回可写交互。

## Migration Plan

部署应用代码后，无需数据库迁移。已有项目的令牌哈希可立即被读取；回滚时移除新路由即可，原有项目数据和管理员后台不受影响。
