## Context

阶段 5 的 `BoardClient` 已持有初始 `ProjectSnapshot`，通过 `projectBoardApi.snapshot(token)` 读取完整快照，并用 `boardReducer` 的 `replace` action 在写入失败或 `409` 冲突后恢复状态。当前项目没有缓存或实时通信依赖，`BoardClient` 也没有周期性或页面生命周期触发的读取逻辑。动机见 `proposal.md`，行为合同见 `interactive-project-board` delta spec。

## Goals / Non-Goals

**Goals:**

- 在不新增后端接口或基础设施的前提下，降低协作者看到其他窗口已保存变更的等待时间。
- 让所有快照读取来源复用同一去重、错误展示和 reducer 替换路径。
- 保护正在进行的乐观写入，不让背景刷新覆盖本地临时状态。

**Non-Goals:**

- 不提供实时、准实时推送、WebSocket、SSE、轮询外的跨浏览器通知或在线状态。
- 不更改既有写入 API、数据库 schema、版本并发控制或项目链接授权。
- 不实现离线缓存、后台标签刷新、全站数据缓存或可配置的用户级刷新频率。

## Decisions

### 复用现有项目快照接口，采用三种前台触发来源

`BoardClient` 抽取单一 `refreshSnapshot` 流程，调用现有 `GET /api/projects/[token]` 并以 `replace` 写入 reducer。该流程由刷新按钮、`focus`、`visibilitychange`（恢复为可见）及每 60 秒的可见页面 interval 触发；首次客户端显示也执行一次，以缩小 SSR 快照到浏览器可操作状态之间的窗口。

这不需要新 API、依赖、部署服务或 token 流转。仅提供刷新按钮会让协作者继续依赖记忆操作；WebSocket 或 SSE 则超出当前“非实时”目标并引入连接、授权与部署复杂度。

### 以单一 inflight 刷新锁协调自动读取与乐观写入

组件用 ref 保证任何时刻最多一个快照请求。自动触发在 `pending` 非空时标记为待刷新而不执行 `replace`；本地 mutation 结束后统一补一次快照读取。手动刷新可复用同一请求，避免用户连点或 `focus` 与 interval 并发导致乱序响应覆盖较新的状态。

写入失败和 `409` 已会重取快照，改造后也进入该共享流程。备选方案是让每个触发源独立调用 fetch；它会产生并发请求、重复错误提示和响应乱序风险。

### 明确刷新状态，但保留最后可信快照

状态模型新增低侵入的 `isRefreshing`、刷新错误及“待刷新”标识；刷新按钮和提示区域说明“正在同步”或失败原因。读取失败不会清空项目、成员或任务；成功读取才替换快照，并使引用已删除实体的对话框按现有安全规则关闭。

这与阶段 5 的失败恢复一致。备选方案是静默刷新，但用户无法判断跨窗口数据是否已更新，也无法主动重试。

## Risks / Trade-offs

- [另一窗口刚写入，当前窗口尚未到下一次触发] → 最多等待 60 秒，或通过切回页面/刷新按钮立即拉取；这是有意接受的非实时延迟。
- [自动刷新与乐观写入重叠] → 使用 pending 感知和单一 inflight 锁，写入完成后补拉快照。
- [弱网下多次 focus 或可见性切换] → 合并为一个进行中的读取，失败保留最后可信状态并提供重试。
- [轮询产生额外读取负载] → 只在可见项目页运行，间隔不短于 60 秒；项目规模扩大时可再考虑条件请求或缓存层。

## Migration Plan

1. 在 `BoardClient` 和 reducer 增加共享刷新状态与去重快照读取流程，复用现有快照 API。
2. 接入手动入口、页面焦点/可见性监听以及仅前台运行的 60 秒定时器；确认卸载时清理监听和计时器。
3. 补充组件与 reducer 测试，并用两个窗口验证刷新、后台恢复、写入冲突与网络失败。
4. 若需回滚，移除客户端触发器和刷新入口即可；现有 API、写入与持久化数据不受影响。
