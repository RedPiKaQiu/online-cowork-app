## Context

当前仓库使用 Next.js、PostgreSQL、Drizzle 与环境变量形式的单管理员配置；既有 `remote-database-deployment` 规范已限制数据库网络暴露并要求可恢复备份。阶段 7 要在不改变既有业务 API 契约的前提下，建立从提交到生产、运行监测及故障恢复的闭环。动机见 [proposal.md](proposal.md)，行为约束见 `production-deployment-operations` delta spec。

## Goals / Non-Goals

**Goals:**

- 形成平台无关、可由 CI/CD 或人工受控执行的发布 runbook。
- 将发布前验证、迁移顺序、生产配置校验、健康检查、错误监控、备份恢复与回滚串联为可追溯流程。
- 覆盖最终产品目标的关键路径：管理员管理项目、匿名项目链接访问、任务和成员变更，以及已实现的项目快照定时刷新。

**Non-Goals:**

- 不指定 Vercel、Docker、Kubernetes 或某一云厂商为唯一部署方式。
- 不在本变更中实现多管理员、细粒度权限、评论/附件、实时协作通道或其他新业务功能。
- 不将数据库迁移设计为自动回滚；数据库回退以迁移兼容性评审和备份恢复为准。

## Decisions

### 以不可变构建与四项质量门禁作为发布输入

发布候选固定为通过 `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build` 的同一提交产物，并记录提交 SHA/版本号。

- 选择理由：与运行平台解耦，且覆盖当前 Next.js 项目的最低质量面。
- 备选方案：仅依赖部署平台构建。未采用，因为无法明确保证 lint、类型检查和测试均已运行。

### 迁移前置、seed 与生产发布严格分离

发布任务先验证受控环境变量，再执行 `pnpm db:migrate`，迁移成功后切换应用流量；`pnpm db:seed` 仅允许本地/测试环境调用。对含破坏性或不可逆变更的迁移，先完成备份并在预览环境演练。

- 选择理由：避免新代码先访问旧结构，也避免生产数据被示例数据污染。
- 备选方案：应用启动时自动迁移。未采用，因为失败会把启动可用性与数据库变更耦合，且难以审计和回滚。

### 分离存活、就绪与业务冒烟验证

健康端点只返回最小状态：存活检查确认进程响应，就绪检查确认必要依赖可用；二者均不返回数据库 URL、token、用户或项目数据。流量切换后使用专用测试项目或隔离验证数据执行业务冒烟测试，检查管理员登录、项目链接访问、任务写入与项目快照定时刷新。

- 选择理由：基础设施可安全轮询健康端点，业务验证则能发现单纯 HTTP 200 无法覆盖的鉴权与数据链路故障。
- 备选方案：使用真实客户项目做验证。未采用，因其会改变真实协作数据并暴露访问凭据。

### 可观测性遵循最小敏感数据原则

服务端错误监控附带版本、环境、请求路由和匿名化关联 ID；日志经统一脱敏，禁止记录 `DATABASE_URL`、Cookie、完整项目 token、密码和会话密钥。为 5xx 错误率、连续就绪失败和异常响应延迟建立告警。

- 选择理由：满足故障定位与审计需要，同时保护持有 URL 即可访问的项目链接模型。
- 备选方案：完整请求日志。未采用，因为 URL token 与认证信息可能被意外持久化。

### 备份优先于数据库回滚

数据库按既定周期自动备份，保留恢复权限、位置、保留期和恢复演练记录。应用版本可回退至上一个不可变产物；数据库仅在迁移向后兼容时随应用回退，否则从发布前备份恢复，并优先在隔离环境确认。

- 选择理由：大多数 schema 迁移难以安全自动逆转，备份恢复更可预测。
- 备选方案：为每个迁移维护 down migration。未采用，因为它不能覆盖数据丢失或语义转换的风险。

## Risks / Trade-offs

- [监控平台或备份提供方故障导致信号缺失] → 对备份任务和监控上报本身设置失败告警，并定期测试告警通道。
- [迁移扩大停机窗口或无法兼容旧版本] → 采用扩展/迁移/收缩策略；发布前在预览数据库演练，并准备维护窗口与恢复点。
- [健康检查连接数据库造成高负载] → 使用轻量查询、超时和合理轮询间隔；仅就绪检查访问依赖。
- [冒烟测试凭据泄露或污染数据] → 使用最小权限的专用验证账号和独立测试项目，定期轮换并在验证后清理可恢复测试数据。
- [审计日志被用作敏感信息载体] → 对字段做显式白名单并在测试中验证 token、Cookie 和密钥均被脱敏。

## Migration Plan

1. 在预览环境补齐质量门禁、健康检查、错误监控、审计日志和部署文档，并用与生产同类的数据库执行迁移演练。
2. 为生产配置密钥托管、HTTPS、备份计划、监控告警和上一稳定版本产物；发布前验证恢复步骤。
3. 执行发布前检查，创建并验证数据库备份，运行迁移；仅在迁移成功和就绪检查通过后切换流量。
4. 运行发布后冒烟验证并观察错误率、健康状态和性能指标；异常时先回退应用流量，再按迁移兼容性或备份恢复处理数据库。
5. 记录版本、迁移、验证、告警和回滚（如有）的结果，更新部署 runbook。
