## Context

见 `proposal.md` 的动机。阶段 3 的服务端页面已经用 `ProjectSnapshot` 加载安全链接项目，阶段 4 已提供项目、成员、任务和排序的写入路由及版本冲突响应。当前 `BoardClient` 仅展示快照；旧 `CoworkBoard` 包含所需的拖拽和弹窗交互，却把全部业务数据保存在 `INITIAL_*` 常量和组件 state 中。项目当前没有 TanStack Query 依赖。

## Goals / Non-Goals

**Goals:**

- 在不改变既有 API 或数据库 schema 的前提下，让 `/p/[token]` 成为唯一的交互式协作看板。
- 以单一客户端状态模型支撑乐观更新、服务端响应合并、失败恢复和后续阶段 6 的实时事件合并。
- 保留当前交互与视觉组件，修复它们依赖 Demo 数据和全局成员的假设。

**Non-Goals:**

- 不增加实时连接、订阅授权、事件发布或跨浏览器即时同步。
- 不新增项目切换、项目创建或管理员功能。
- 不引入离线队列、CRDT、批量编辑或新的状态管理依赖。

## Decisions

### 使用 `useReducer` 保存规范化项目快照与界面状态

`BoardClient` 接收服务端初始 `ProjectSnapshot` 与 token，并以 reducer 管理当前快照、临时任务、进行中的实体标识、错误提示以及拖拽/抽屉/对话框状态。任务在 reducer 内按 `status` 分组，所有 mutation 的成功 DTO 和未来实时事件都通过同一组 upsert、remove、replace-column action 合并。

选择 `useReducer` 是因为状态集中且目前没有缓存库依赖；它能在不增加包的情况下明确描述乐观变化和回滚。替代方案是 TanStack Query：其缓存与 mutation 机制合适，但为当前单页、单资源场景引入额外依赖和模式成本；后续数据范围扩大时可再迁移。

### 以乐观变更加服务端响应确认的方式执行 mutation

客户端封装 JSON 请求、非成功响应解析和 `GET /api/projects/:token` 快照重取。操作前生成 `crypto.randomUUID()` 作为本地关联标识；重排请求同时将其作为 API 所需的 `mutationId`。创建任务先加入带本地 ID 的临时项，成功后替换为服务端任务；更新、分配、删除与移动先在 reducer 中变更，再以响应 DTO 或受影响列确认最终状态。

请求失败、超时或 `409` 时丢弃失败操作的临时状态、显示响应错误，并重取完整快照；快照重取失败时保留最后一次服务端确认快照并显示恢复失败提示。替代方案是分别手写局部反向操作：它在交叠 mutation、成员删除导致取消分配及排序变化时容易遗漏，完整快照恢复更可靠。

### 版本和实体请求按 API 合同携带

项目编辑使用项目 `version`；任务 PATCH、DELETE 和 reorder 使用当前任务 `version`。成员 API 不要求版本。对于同一任务或项目，在已有写入未完成时禁用或忽略新的同实体提交；不同实体仍可并行操作。任务进入 `box` 时先在乐观状态清空负责人，以匹配服务端领域规则。

这避免客户端明知陈旧的版本继续叠加变更，并与阶段 4 的冲突边界一致。替代方案是全局锁住整个看板，虽更简单但会无谓阻塞成员或其他任务操作。

### 组件边界保持展示组件轻量、由容器注入回调

`BoardClient` 负责 token、状态和 API mutation；`TaskCard`、`QuickAddBar`、`MemberManager`、`TaskEditDialog`、`DoneDrawer` 与 `TaskColumn` 接收数据、loading 状态及意图回调。任务卡片新增明确删除入口和确认流程。`lib/board-data.ts` 仅保留可由这些组件共享的 `ColumnId`、任务/成员显示类型、查找函数和色彩常量；移除初始项目、初始成员和 ID 生成器。`CoworkBoard` 与 `ProjectSwitcher` 不再由项目页面引用，可在迁移完成后删除或仅保留管理员页面实际需要的部分。

这使 UI 可以在不接触 fetch 细节的情况下复用，也为阶段 6 把事件送入同一 reducer 留出接口。替代方案是每个子组件自行请求 API，会让错误处理、token 使用和快照一致性分散。

## Risks / Trade-offs

- [同时执行多个 mutation 后其中一个失败] → 使用完整快照重取作为最终恢复路径，并将乐观项标记为进行中以限制同实体重复提交。
- [刷新请求本身失败] → 保留最后一次已确认快照、显示可重试提示，不把乐观状态误称为已保存。
- [临时任务与服务端 ID 交替时弹窗仍引用旧对象] → 以 ID 解析当前任务；替换或移除后关闭无效对话框和抽屉上下文。
- [删除旧 Demo 组件影响未发现的入口] → 先用全仓引用搜索确认无调用方，再删除无用导出；以 typecheck 和组件测试验证。
- [阶段 6 需要更细粒度合并] → reducer 的实体/列 action 不绑定 HTTP 响应来源，实时事件可复用它们。

## Migration Plan

1. 提炼共享类型与客户端请求/状态归约工具，删除运行时 Demo 数据依赖。
2. 将当前 `CoworkBoard` 的交互迁入 `BoardClient`，由项目 token 调用阶段 4 API，并逐项接入成功确认与失败恢复。
3. 为加载、空状态、进行中、网络失败和 `409` 冲突补充界面测试，验证刷新后从持久化快照恢复。
4. 在本地和预览环境手工验证任务、成员、排序和删除；确认不再存在项目切换入口。
5. 此变更不迁移数据。若需回滚，部署上一版本即可；已写入的数据仍由阶段 4 的既有 schema 与读取接口兼容。
