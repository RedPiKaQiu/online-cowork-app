## Context

任务快照按持久化 `position` 返回；同状态的 `updateTask` 不会修改该值。当前客户端统一处理任务写入结果时先移除事项，再将其追加到目标列末尾，因此同列编辑产生临时排序偏差。

## Goals / Non-Goals

**Goals:**

- 让同列任务编辑在乐观更新和服务端确认两个阶段均保持原索引。
- 保持跨列移动、新建事项和拖拽重排的既有排序语义。

**Non-Goals:**

- 不修改数据库的 `position`、任务写入 API 或排序事务。
- 不引入新的同步协议或全局客户端排序机制。

## Decisions

- `task-upsert` 在移除旧任务前记录其所在列与索引；若更新后的状态仍在该列，则把更新后的任务插回该索引。这样乐观编辑和响应确认使用同一条规则。
- 当状态改变或没有可替换的旧任务时，继续追加至目标列末尾。跨列状态更新的服务端语义本来就是分配目标列末尾位置；拖拽重排仍由 `columns` 动作以服务端完整列结果确认。
- 使用 reducer 单元测试覆盖同列更新，直接验证更新后任务 ID 顺序不变。相较于在组件调用方传递额外索引，这能集中定义所有 upsert 的顺序语义。

## Risks / Trade-offs

- [响应与乐观状态的关联任务 ID 不同] → 同时匹配响应 ID 与 `previousId`，以便服务端创建结果替换本地临时事项时仍保留位置。
- [跨列移动被错误地保留源列索引] → 仅在旧列与目标列相同的条件下复用索引。

## Migration Plan

该变更仅调整客户端内存状态，无数据迁移。若需回滚，恢复原 reducer 行为即可；数据库中的持久化位置始终未受影响。
